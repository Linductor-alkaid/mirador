# Mirador 项目管理与工程规范

> 状态：Active
> 版本：1.0
> 生效日期：2026-09-13
> 适用范围：Mirador 的代码、测试、设计、计划、决策、验证记录、发布材料和 Git 仓库操作

本规范由 Mira（Agent Runtime）与 Heyaki（设备通信基础设施）两个 C++20 项目的实践归纳而成：
项目管理与文档规则以 Mira 的 `docs/project/project_management_and_documentation.md` 为基础，
里程碑拆分、稳定编号、退出条件和验证记录方法沿用 Heyaki 的总计划结构，Git 提交与 MR 规范
来自团队《Git Commit / Merge Request 提交规范》并补充标准仓库管理方法。Mirador 不引入统一
并发框架：核心为同步 API、无内部并发设施（见根 `AGENTS.md`），模板中原有的 Executor 依赖
纪律已按[设计文档](../design/mirador-development-design.md)的边界裁剪，替换为第 9 节的依赖
与可选模块规范。

## 1. 目的与规范效力

本文定义项目的规划、任务跟踪、技术决策、文档编写、验证取证、依赖与并发边界、Git 仓库管理
和变更同步规则。目标是让每项工作都能回答：为什么做、由什么设计约束、当前做到哪里、如何证明
完成，以及后续如何复现结论。

仓库内规则按以下顺序解释：

1. 用户或维护者对当前工作的明确要求。
2. 根目录 `AGENTS.md` 中的仓库级强制约束。
3. 本文中的项目管理与工程规范。
4. 已批准的设计文档和决策记录。
5. 总计划、里程碑计划和工作项中的局部约定。

低层文档不得静默覆盖高层约束。若实现需要改变已生效的架构、公开契约、安全边界、依赖与并发
边界或产品默认值，必须先新增或更新决策记录，再同步修改设计、计划和测试。

文档承担不同职责，不互相替代：

- 设计文档说明系统应如何工作以及为什么这样设计。
- 决策记录说明一个有实质影响的选择、备选方案和后果。
- 计划文档说明交付顺序、范围、状态、依赖和验收方式。
- 测试及验证记录说明某项声明在什么条件下得到证明。
- 代码和配置是实际行为的实现，但不能作为缺失契约文档的长期替代品。

## 2. 文档目录

文档按用途放置；目录在出现首份对应文档时创建：

| 路径 | 内容 | 典型文件 |
| --- | --- | --- |
| `docs/design/` | 架构、模块、协议、状态机和跨层契约 | `<domain>_design.md` |
| `docs/decisions/` | 架构决策和产品默认值记录 | `DEC-001-<topic>.md` |
| `docs/plans/` | 总计划、里程碑计划和交付清单 | `mirador-implementation-plan.md`、`m0-<scope>.md` |
| `docs/security/` | 威胁模型、安全策略、隐私和凭据处理 | `threat-model.md` |
| `docs/compatibility/` | 平台、编译器、依赖和 Provider 兼容性证据 | `<dep>-<version>.md` |
| `docs/supply-chain/` | 依赖锁定、许可证、SBOM 和升级审计 | `dependency-policy.md` |
| `docs/benchmarks/` | 性能目标、方法、原始条件和结果摘要 | `<metric>-latency.md` |
| `docs/project/` | 本规范及其他仓库级协作流程 | 本文 |

不要用一个"总文档"承载所有内容。安全结论、兼容性声明、性能数据和供应链证据应保留在各自
目录，由设计或计划通过相对链接引用。

## 3. 项目规划层级

### 3.1 总计划

总计划是项目交付范围与进度的唯一入口，见 `docs/plans/mirador-implementation-plan.md`。它包含：

- 当前整体状态和最近更新时间。
- 交付边界条目（`SCOPE-NN`）：确认包含与明确不包含的能力，逐条可勾选。
- 不可破坏的架构约束（`RULE-NN`）：分层、所有权、依赖边界、安全、容量和验证底线。
- 里程碑索引、依赖关系和建议发布点（里程碑应产生可独立验收的能力增量，仅以目录、分工或
  时间周期划分的内容不适合作为里程碑）。
- 尚未冻结的产品或技术决策（`DEC-NNN` 暂定默认值）及其负责人和最迟冻结里程碑。
- 跨里程碑通用完成定义（`DOD-NN`）。
- 建议的拆分与合并顺序：先骨架后功能、先契约后实现、先 SPI/假实现后真实依赖。
- 延后项与触发条件（`POST-NN`）：明确什么证据出现时才立项。

总计划保持概览性质。具体任务、测试和逐轮实施证据放到独立里程碑文档，避免总计划因流水
记录而失去可读性。

### 3.2 里程碑计划

每个里程碑使用独立文件，例如 `docs/plans/m0-<scope>.md`，并必须声明：

- 状态、负责人、所属总计划和最后更新时间。
- 目标、范围、非目标、前置依赖和建议发布点。
- 带稳定编号的工作项。
- 测试矩阵和退出条件。
- 风险、阻塞项及相关设计或决策链接。
- 按日期追加的实施与验收记录。

### 3.3 工作项与编号体系

工作项是可验收的最小计划单位，使用 `M<里程碑>-<两位序号>`，例如 `M1-03`。一项工作应描述
结果而非活动：使用"提供可组合的 `Transform2D` 变换并通过往返容差测试"，而不是"研究坐标变换"。

工作项必须能关联到至少一项验收方式。预计需要跨多个模块、无法由单次评审验证或包含多个
独立结果时，应拆分为多个工作项。

计划内其他编号系列：

| 前缀 | 用途 | 示例 |
| --- | --- | --- |
| `SCOPE-NN` | 总计划交付边界条目 | `SCOPE-01` |
| `RULE-NN` | 总计划不可破坏架构约束 | `RULE-07` |
| `DOD-NN` | 总计划通用完成定义条目 | `DOD-08` |
| `POST-NN` | 延后项及其立项触发条件 | `POST-03` |
| `DEC-NNN` | 架构或产品决策记录 | `DEC-004` |
| `BUG-YYYYMMDD-NNN` | 需要跨提交跟踪的重要缺陷 | `BUG-20260913-001` |
| `RISK-YYYY-NNN` | 影响里程碑或发布的已识别风险 | `RISK-2026-02` |

编号一经被引用不得复用；项目扩大到编号冲突时可增加领域前缀，但同一文档内必须一致。

## 4. 状态与勾选规则

计划、里程碑和工作项使用以下状态词，不自造含义相近的状态：

| 状态 | 含义 |
| --- | --- |
| `Proposed` | 已提出，范围或方案尚待评审 |
| `Planned` | 范围、依赖和验收方式已明确，可排期 |
| `In Progress` | 已开始实施，尚未满足完成定义 |
| `Blocked` | 有明确外部阻塞，已记录负责人和解除条件 |
| `Completed` | 实现和全部适用退出条件已通过 |
| `Superseded` | 已由另一文档或决策替代，保留历史链接 |
| `Cancelled` | 明确终止且不再计划交付，保留原因 |

决策记录使用 `Proposed`、`Accepted`、`Superseded` 或 `Rejected`：`Accepted` 表示已批准并生效，
`Rejected` 表示经评审未采用。决策状态不用于表示实施进度；其落地进度由关联的计划工作项跟踪。

清单勾选必须遵守以下规则：

1. 只有实现、测试、必要文档和本项验收均完成后，才能从 `[ ]` 改为 `[x]`。
2. "代码已写完""本机能编译"或"提交已合并"本身不等于完成。
3. 因设备、权限、网络、凭据或平台缺失而未执行的验证必须保持 `[ ]`，不得用 skip、预期通过
   或其他平台的结果冒充成功。
4. 未执行项必须记录原因、所需环境、负责人和可操作的补跑条件。
5. 工作项全部完成不自动关闭里程碑；所有退出条件也必须逐项通过并留下验证记录。
6. 重新打开已完成工作时保留原验证记录，说明失效原因，并将状态或复选框恢复为未完成。

## 5. 准入与完成定义

### 5.1 Definition of Ready

非平凡工作进入 `In Progress` 前至少满足：

- 目标、范围和非目标可被复述且没有关键歧义。
- 所属里程碑或维护任务明确，并已有稳定编号。
- 相关设计、决策和公开契约已定位；需要改变它们时已有同步更新安排。
- 依赖、风险、平台条件和并发承载方式已识别。
- 验收标准可执行，所需测试环境已知。
- 涉及用户数据、凭据或外部副作用时，安全与恢复行为已定义。

小型拼写修复、无行为变化的格式调整等可不创建独立计划项，但仍必须遵守相关文档规则。

### 5.2 Definition of Done

一项变更只有同时满足以下条件才可完成：

- 实现符合分层、所有权、取消、错误和依赖边界约束。
- 新增或变更行为具有与风险相称的自动化测试。
- 适用的构建、测试、静态检查、平台验证或基准已经执行并通过。
- 公开 API、错误语义、缓存键语义、配置和示例已同步更新。
- 受影响的设计、决策、计划、安全、兼容性和供应链文档已同步更新。
- 验证记录包含可复现证据；未验证声明被明确限定。
- 不存在被吞掉的失败、无主后台任务、未闭合取消路径或未登记的依赖边界绕行。
- Commit 与 MR 符合第 10 节规范，评审意见已全部回复或处置。

## 6. 文档模板

### 6.1 里程碑文档模板

新建里程碑文件时使用以下基本结构，可按领域增加小节，但不能删除状态、任务、退出条件和
验证记录：

```md
# M1：里程碑名称

> 状态：Planned
> 负责人：姓名或团队
> 所属计划：Mirador 实施总计划（创建文件时改为实际相对链接）
> 前置：M0
> 建议发布点：<release-tag>
> 更新日期：YYYY-MM-DD

## 目标

## 范围与非目标

## 设计与决策依据

## 工作项

- [ ] `M1-01` 以可验收结果描述任务。

## 风险与阻塞

## 测试与退出条件

- [ ] 给出可观察、可执行的通过条件。

## 验证记录

YYYY-MM-DD：记录 commit、环境、命令、结果、限制和剩余项。
```

验证记录按时间追加。可以修正事实错误，但不得重写历史使失败、回退或环境限制消失。

### 6.2 决策记录模板

以下变化必须建立或更新 `docs/decisions/` 中的记录：跨模块依赖方向与生命周期；公开 API、
持久化格式、事件 schema 或兼容性承诺；核心契约；安全边界与默认权限；关键依赖、支持平台、
性能目标或产品默认值；明显改变实现复杂度或未来扩展方向的取舍。

```md
# DEC-NNN：决策标题

> 状态：Proposed | Accepted | Superseded | Rejected
> 日期：YYYY-MM-DD
> 负责人：姓名或团队
> 冻结里程碑：M1
> 替代/被替代：无

## 背景与问题

## 决策

## 备选方案

## 影响与风险

## 验证方式

## 关联文档和工作项
```

尚待确认但为推进验证而采用的选择必须标为"暂定默认值"，同时填写负责人和最迟冻结里程碑，
不能把暂定值写成既定事实。推翻既有决策时，新记录应链接旧记录，旧记录改为 `Superseded`
并反向链接新记录。禁止删除已被代码、计划或发布说明引用的历史决策。

### 6.3 最小变更记录模板

非里程碑性质但需要留存的实施记录可使用：

```md
## YYYY-MM-DD：M1-03 简短结论

- 范围：本次实际改变的行为。
- 依据：关联设计和 `DEC-NNN`。
- 验证：平台、配置、准确命令及结果。
- 限制：未执行项、原因、负责人和补跑条件。
- 同步：已更新的计划、设计、测试及兼容性文档。
```

该记录可以放在对应里程碑的"验证记录"中。不要为每个小提交创建孤立报告；记录粒度应足以
支持里程碑验收、问题定位和结论复现。

## 7. 验证证据

每条重要验收记录应包含：

- 日期和对应 commit 或工作树状态。
- 操作系统、架构、设备或模拟器、编译器和关键依赖版本。
- 构建类型、feature flags 等影响结果的条件。
- 可复现的准确命令或 CI job/run 链接。
- 通过、失败或未运行的结果，以及关键计数或指标。
- 已知限制、失败归属、负责人和补跑条件。

以下声明必须区分证据等级：

| 声明 | 最低证据 |
| --- | --- |
| 源码或配置支持 | 对应代码、配置和静态检查 |
| 可以编译 | 指定工具链和配置的实际构建结果 |
| 可以运行 | 目标环境中的运行或集成测试 |
| 可互操作 | 与明确版本对端的端到端验证 |
| 满足性能目标 | 固定方法、样本、硬件和统计结果 |
| 坐标恢复正确 | 方向、stride、奇数尺寸与往返容差测试矩阵 |
| 跨平台支持 | 每个被声明平台的构建和适用运行门禁 |

测试 skip 是诊断结果，不是成功证据。日志可以作为附件，但验收记录还应给出人可读的结论，
不能只贴一段无法定位环境和退出码的输出。

## 8. 文档同步矩阵

实现变更时按下表检查同步范围：

| 变更类型 | 必须检查或更新 |
| --- | --- |
| 公开 API、接口或错误语义 | 设计、头文件注释、示例、测试、兼容性说明 |
| 坐标模型或变换语义 | 设计、变换测试矩阵、Backend 适配文档、示例 |
| 并发边界、取消或 deadline 语义 | 设计、`ExecutionContext` 约定、线程安全声明与竞态测试 |
| 缓存键、失效或淘汰策略 | 设计、负向测试（模型修订/参数/ROI/预处理版本）、预算说明 |
| 安全或隐私边界 | 威胁模型、决策、负向测试和日志脱敏规则 |
| 产品或技术默认值 | 决策记录、总计划、配置、测试和迁移说明 |
| 依赖版本或构建组合 | 锁定信息、兼容性矩阵、许可证/SBOM 和回归记录 |
| 性能声明 | benchmark 方法、结果、目标平台限制和计划门禁 |
| 里程碑范围或状态 | 总计划索引、里程碑文档、依赖方和验证记录 |

同步更新应与实现处于同一变更中。确实需要分阶段完成时，相关工作项保持未完成，并记录
后续编号和负责人，不能以"以后补文档"关闭当前范围。

## 9. 依赖与可选模块规范

### 9.1 定位与锁定

Mirador 核心只依赖 C++20 标准库；OpenCV、ELSED、字体渲染等仅为对应可选模块的实现依赖
（见设计文档第 3、21 节）。可选第三方依赖以 pinned 形式引入，两种可接受的锁定方式：

- **Git submodule + 锁文件**：`.gitmodules` 声明 `third_party/<dep>`，`dependencies.lock.json`
  记录 source、精确 commit、版本号、许可证及许可文件路径；CMake configure 时校验 commit。
- **lock 清单 + CMake 拉取**：`third_party/dependencies.lock` 逐行记录
  `name|url|pinned_commit|expected_commit|submodule|class`，configure 时同步缺失仓库并
  校验 commit；离线/CI 构建可用 `-DMIRADOR_FETCH_DEPENDENCIES=OFF` 走只校验路径。

使用系统包管理器安装的依赖（如 CI 中的 OpenCV）必须在 `docs/compatibility/` 记录已验证
版本区间，并在 CI 中固定版本。未经明确授权不得修改 pinned 依赖源码；升级必须记录旧版本、
新版本、能力变化、受影响范围和回归结果。

### 9.2 强制规则

1. `mirador-core` 的链接闭包只允许 C++20 标准库；由架构测试锁住该边界并在 CI 运行。
2. 可选依赖只能被对应模块的可选编译单元引用，公共头不得包含其任何类型；互操作经
   `adapters/` 提供并在文档中标注为非核心能力。
3. 可选依赖对应的 CMake 选项默认关闭，最小核心构建不得获取、编译或链接它们。
4. 模型权重、数据集与生成产物不进入源码树；示例通过用户显式提供的路径访问外部资源。
5. 引入或升级可选依赖走独立 MR，并在 `docs/supply-chain/` 记录许可证、来源、SBOM 影响
   与审计结论；`THIRD_PARTY_NOTICES` 与实际分发内容保持同步。
6. 具体模型 runtime 的 Backend 示例位于独立仓库或默认构建不获取的 `integrations/`；
   不得使默认构建隐式下载 runtime 或模型。

### 9.3 选型与审查流程

引入新的可选依赖前：先核对候选依赖的许可证、维护状态、目标平台支持（Android NDK/Linux/
Windows）与体积影响，形成对比记录；按第 6.2 节建立决策记录后再实施；引入时同步锁定信息、
兼容性记录与供应链文档。ELSED 等以源码引入的算法库必须先完成许可证审查。

### 9.4 边界例外流程

不得为绕过依赖边界而静默引入另一套实现。当确认某个能力确实无法在现边界内实现时：

1. 先核对设计文档与现有模块，排除 API 选型错误与应用层职责错位。
2. 按第 6.2 节建立或更新决策记录，说明缺口、备选方案、影响与验证方式；只写"需要依赖"
   不构成有效记录。
3. 在相关代码、测试与设计文档中引用该决策编号，并同步架构测试。
4. 确需临时方案时，将其限制在单一适配边界内，说明行为差异、风险、移除条件和测试覆盖；
   临时方案不得创建线程、后台任务或调度器。

以下情况不是依赖边界缺口：具体平台采集、Accessibility 数据获取、VLM 提示构造、动作执行、
业务策略。它们属于调用方或适配层职责。

## 10. Git 仓库管理

### 10.1 分支模型与命名

- 采用主干开发模型：`master`（或 `main`）是唯一长期分支，始终保持可构建、可测试。
- 功能工作在短生命周期特性分支上进行，命名 `feat/<scope>-<description>`、`fix/<scope>-<description>`、
  `docs/...`、`refactor/...`、`perf/...`、`test/...`、`ci/...`；使用 Agent 协作时可统一加
  agent 前缀（如 `codex/<type>/...`）。
- 特性分支存活时间应尽量短；长期分支须定期同步主干，合并前必须 rebase 或 merge 最新主干
  消除冲突。
- `master` 设为保护分支：禁止直接 push，只能通过 MR/PR 合入，且合入前 CI 必须通过、评审
  必须完成。不得 force-push、改写已发布历史或在未获用户明确要求时重写公共分支。
- 修复紧急问题的 `hotfix/<issue>` 分支从 master 切出，修复后同时合回 master 与进行中的
  发布分支（若存在）。

### 10.2 Commit Message 规范

统一采用格式：

```text
<type>(<scope>): <subject>
```

其中 `scope` 为可选项，用于说明本次修改涉及的模块；同一仓库内部保持一致。本仓库 scope
词表：`core`、`image`、`cache`、`geometry`、`fusion`、`render`、`adapters`、`examples`、
`benchmarks`、`tests`、`build`、`ci`。

| type | 说明 |
| --- | --- |
| `feat` | 新增功能 |
| `fix` | Bug 修复 |
| `refactor` | 代码重构，不改变已有功能 |
| `perf` | 性能优化 |
| `docs` | 文档修改 |
| `test` | 测试相关修改 |
| `build` | 编译系统、依赖相关修改 |
| `ci` | CI/CD 配置修改 |
| `chore` | 其他工程性修改 |
| `revert` | 回滚已有提交 |

推荐优先使用 `feat`/`fix`/`refactor`/`perf`/`docs`/`test`。示例：

```text
feat(core): define status and result error model
fix(image): correct letterbox coordinate recovery for odd sizes
refactor(cache): simplify bounded LRU eviction
docs: update change detection design
```

避免含义不明确的提交说明（`update`、`modify`、`fix bug`、`临时修改`、`final2` 等）。

**Commit 颗粒度**：一个 Commit 对应一个相对独立的逻辑修改；不为追求小提交产生大量无意义
提交。开发过程中允许临时 Commit，但提 MR 前应通过 rebase/squash 整理提交历史。

**提交前检查**：

```bash
git status
git diff
git diff --cached
```

确保 Commit 中：只包含本次修改相关内容；不包含无关格式化修改、临时 Debug 代码、运行日志、
编译产物、IDE 临时文件、不必要的大文件，以及密码、Token、Key 等敏感信息。提交中不得携带
与本变更无关的工作树改动。

**提交身份**：`user.name` 与 `user.email` 必须是提交者本人配置，严禁使用他人身份提交。

### 10.3 Merge Request 规范

**标题**：与 Commit 保持类似格式 `<type>(<scope>): <description>`。一个 MR 只解决一个明确的
问题或实现一个完整功能；修改之间没有明显关联时应拆分为多个 MR。

**描述**至少包含四部分：

1. 修改内容：本次 MR 改了什么（如新增模块的行为、参数与工作模式）。
2. 修改原因：为什么需要此次修改（当前缺失或缺陷是什么）。
3. 测试情况：明确说明实际完成的测试（如"编译通过；坐标往返变换测试通过"）。禁止在未执行
   测试的情况下填写"测试通过"。
4. 影响范围：涉及 API/ABI、公共契约、缓存键语义、配置文件、参数、数据格式、第三方依赖或
   构建选项时逐项说明。

**MR 大小**：保持在 Reviewer 可以理解和有效 Review 的范围内。大型需求按
`基础接口 → 核心实现 → 功能接入 → 测试 → 优化` 拆分；无法拆分的大型重构应提前沟通并在 MR
中说明设计思路和影响范围。

### 10.4 Code Review 与合并

- 原则上至少经过一名相关开发人员 Review。Reviewer 重点检查：实现逻辑、边界条件、异常处理、
  接口兼容性、依赖边界、潜在回归风险、代码可维护性、测试覆盖情况。
- Review 意见明确区分：`必须修改`、`建议修改`、`讨论项`。开发人员完成修改后应回复对应
  comment，避免问题处于未确认状态。
- 合并条件：

```text
开发完成 + 自测通过 + 目标分支已同步 + 无代码冲突 + CI 通过 + Code Review 通过
```

- 合并策略从 `Merge Commit` / `Squash and Merge` / `Rebase and Merge` 中团队统一选择一种：
  普通功能开发推荐 Squash and Merge 保持主线简洁；需要保留完整 Commit 历史的大型功能可按
  实际情况保留。

### 10.5 版本与发布

- 版本号遵循语义化版本（`vMAJOR.MINOR.PATCH`），tag 打在对应发布点 commit 上并附简短说明；
  里程碑文档的"建议发布点"与 tag 一一对应。
- 维护 `CHANGELOG.md`，按版本记录功能、修复、兼容性影响和依赖变化。
- 发布前核对：依赖锁定与 SBOM 可重复生成、许可证清单完整、兼容性矩阵中声明的平台均有
  构建与运行门禁证据、已知限制已写入发布说明。
- 不发布未通过目标平台或基准验证的性能或跨平台声明。

### 10.6 仓库卫生

- `.gitignore` 覆盖构建目录（`build/`）、生成文件、测试产物、IDE 配置和凭据文件；提交前
  确认 `git status` 无计划外文件。
- 模型权重、数据集等大文件使用外部存储并在文档中记录获取方式，不直接随普通 Commit 提交。
- 日志、截图与验证产物过大或含敏感数据（截图可能含账号、聊天与支付信息）时不提交仓库；
  文档记录受控存储位置、摘要、保留期限和复现方法，公开内容提交前必须脱敏。
- 不在远程 URL、进程参数、命令输出或日志中暴露认证 token；凭据经系统 keyring 或受管配置
  注入。

### 10.7 依赖锁定与升级（Git 视角）

- `third_party/` 依赖一律 pin 到精确 commit 并在 lock 文件（`dependencies.lock.json` 或
  `third_party/dependencies.lock`）中登记来源、版本、许可证与校验 commit；configure 阶段
  校验，不匹配即失败。
- 依赖升级走独立 MR：更新 pin、说明版本差异与许可证变化、运行全量回归，并在
  `docs/supply-chain/` 记录审计结论。
- 生成物（协议文件、fixture、fuzz corpus）约束在构建树内，不进入源码树。

## 11. C++ 工程基线

- 语言标准 C++20；构建统一走 CMake（项目最低 3.16，使用预设需 ≥ 3.21，开发与 CI 建议
  ≥ 3.25，见 `DEC-005`）+ `CMakePresets.json`，至少提供 `debug`、`release`、`asan`、
  `ubsan`、`tsan` 预设及对应 `ctest` 入口。
- 以 CMake target 表达依赖方向；公共头不得包含第三方私有类型；以架构测试锁住核心链接
  闭包（仅标准库、无线程/调度设施），CI 必须运行该测试。
- 仓库根放置 `.clang-format` 与 `.clang-tidy`，CI 执行格式与静态检查；关键警告按仓库策略
  设为 error。
- 测试打标签（`unit`、`property`、`architecture`、`integration`、`security`、`performance`、
  `platform`、`fuzz`），CI 不以"无测试可运行"冒充成功；依赖外部环境（设备、模型权重）的
  用例在缺失时显式 skip 并记录补跑条件。
- ASAN/UBSAN 常规运行；涉及跨 session 状态或共享缓存时增加 TSAN/故障注入；坐标与解析类
  代码加入 fuzz corpus。
- CI 覆盖目标平台矩阵（Linux GCC/Clang、Windows MSVC、Android NDK arm64-v8a），执行
  configure、build、test 和安装后最小 consumer 编译。
- 供应链：所有直接依赖可离线校验，许可证清单与 SBOM（SPDX/CDX）由构建目标再生成。
- 公开 API 变更同步更新示例；示例使用公共 API 并纳入编译或 smoke test。

## 12. Markdown 与链接风格

- 文件名使用小写英文和连字符，稳定编号可保留大写，如 `DEC-004-error-model.md`。
- 标题简洁且层级连续；每个文件只有一个一级标题。
- 使用相对链接连接仓库内文档，链接文字描述内容，不使用"点这里"。
- 表格用于稳定映射和矩阵，长篇论述使用段落或列表。
- 命令、路径、类型、状态和 ID 使用反引号；命令块注明语言 `bash`。
- 日期统一为 `YYYY-MM-DD`，状态和版本在文档开头可见。
- 首次使用缩写时解释含义，公共术语与设计文档保持一致。
- 修改文档后至少检查相对链接、标题结构、代码围栏和被引用文件是否存在。

## 13. 归档与替代

已完成的里程碑和历史决策保留在原路径，以保证链接和编号稳定。文档不再适用时标记
`Superseded` 或 `Cancelled`，在开头写明替代文档、日期和原因。仅在文件从未形成有效引用、
内容完全错误且版本历史足以追溯时才考虑删除。

## 14. 评审与变更控制

评审重点按以下顺序进行：

1. 是否符合产品目标、范围和既有决策。
2. 分层、所有权、平台边界和依赖边界是否正确。
3. 失败、取消、超时和缓存淘汰是否闭合。
4. 安全、隐私、兼容性和迁移风险是否明确。
5. 测试与验证证据是否足以支撑声明。
6. 文档、计划、Commit/MR 规范和状态是否同步。

发现实现与文档不一致时，不能默认以任一方覆盖另一方。先判断是实现缺陷还是已批准的设计
变化：前者修复实现，后者按决策流程同步所有受影响文档。
